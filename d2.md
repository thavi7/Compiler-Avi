# AviLang --- Day 2 Notes

## What we built today

Today we connected the main stages of Hydro, our compiler:

``` text
AviLang source file (.hy)
        |
        v
   Read source file
        |
        v
     Tokenizer
        |
        v
    vector<Token>
        |
        v
      Parser
        |
        v
       AST
        |
        v
     Generator
        |
        v
   Assembly text (.asm)
        |
        v
       NASM
        |
        v
   Object file (.o)
        |
        v
        ld
        |
        v
    Executable
```

Each component has a separate responsibility:

-   **Tokenizer:** recognizes individual pieces of source code and
    produces tokens.
-   **Parser:** checks how tokens are arranged according to the grammar
    and builds an AST.
-   **Generator:** reads the AST and produces assembly text.
-   **`main.cpp`:** connects the components and runs the assembler and
    linker.

Our current language is deliberately small. The example program is:

``` text
exit(222);
```

# 1. Why does the compiler have multiple stages?

## 1.1 Source code

The user's AviLang program is initially just text in a `.hy` file. The
compiler must interpret that text.

## 1.2 Tokenization: characters become tokens

The Tokenizer reads the source and recognizes individual items.

For example:

``` text
exit(222);
```

is conceptually converted into:

``` text
exit
open parenthesis
integer literal: 222
close parenthesis
semicolon
```

The Tokenizer answers: **What are the individual pieces in this source
text?**

It does not prove that those pieces form a valid statement. For example,
`exit`, `222`, and `;` might all be recognizable tokens in `exit 222;`,
but that arrangement does not match our intended syntax.

## 1.3 Parsing: tokens become structure

The Parser checks whether the tokens match the grammar.

Our intended grammar is conceptually:

``` text
exit_statement -> exit ( expression ) ;
expression     -> integer_literal
```

The Parser also builds an Abstract Syntax Tree (AST).

For `exit(222);`, the AST is conceptually:

``` text
NodeExit
    |
    +-- expr
          |
          +-- int_lit: 222
```

The AST represents the program's structure in a form that later compiler
stages can use.

## 1.4 Code generation: AST becomes assembly text

The Generator receives the AST and creates assembly instructions. For
the current example, it generates:

``` asm
global _start

_start:
    mov rax, 60
    mov rdi, 222
    syscall
```

The Generator returns this assembly as a C++ `string`. It does not
itself write the `out.asm` file in our current code.

## 1.5 Assembling and linking

NASM converts assembly text into an object file:

``` bash
nasm -felf64 out.asm
```

This produces `out.o`.

The linker creates the executable:

``` bash
ld -o out out.o
```

The roles are different:

-   NASM: assembly text → object file.
-   `ld`: object file → executable.

# 2. `parser.hpp` --- understanding and building the AST

Our Parser receives tokens from the Tokenizer. It checks the syntax and
constructs AST nodes.

The code we worked with is:

``` cpp
#pragma once
#include "./tokenization.hpp"

struct NodeExpr {
    Token int_lit;
};

struct NodeExit {
    NodeExpr expr;
};

class Parser {
public:
    inline explicit Parser(vector<Token> tokens)
        : m_tokens(move(tokens))
    {
    }

    optional<NodeExpr> parse_expr() {
        if (peak().has_value() && peak().value().type == TokenType::int_lit) {
            return NodeExpr{.int_lit = consume()};
        } else {
            return {};
        }
    }

    optional<NodeExit> parse() {
        optional<NodeExit> exit_node;

        while (peak().has_value()) {
            if (peak().value().type == TokenType::exit) {
                consume();

                if (auto node_expr = parse_expr()) {
                    exit_node = NodeExit{.expr = node_expr.value()};
                } else {
                    cerr << "Invalid Expression !" << endl;
                    exit(EXIT_FAILURE);
                }

                if (peak().has_value() && peak().value().type == TokenType::semi) {
                    consume();
                } else {
                    cerr << "Invalid Expression !" << endl;
                    exit(EXIT_FAILURE);
                }
            }
        }

        m_index = 0;
        return exit_node;
    }

private:
    inline optional<Token> peak(int ahead = 0) const {
        if (m_index + ahead >= m_tokens.size()) {
            return {};
        } else {
            return m_tokens[m_index + ahead];
        }
    }

    inline Token consume() {
        return m_tokens[m_index++];
    }

    const vector<Token> m_tokens;
    size_t m_index = 0;
};
```

The formatting is normalized for readability. The identifier in the
shared code is spelled `peak`, not `peek`. Both spellings are legal C++
identifiers, but they are different names. The declaration and every
call must use the same spelling.

## 2.1 `#pragma once`

``` cpp
#pragma once
```

This tells the compiler to include this header only once in a single
compilation unit. It helps prevent duplicate-definition problems when
multiple files include the same header.

## 2.2 Include the Tokenizer header

``` cpp
#include "./tokenization.hpp"
```

The Parser needs the `Token` type and token-type definitions declared in
the Tokenizer header. For example, it refers to `Token`,
`TokenType::int_lit`, `TokenType::exit`, and `TokenType::semi`.

## 2.3 AST node: `NodeExpr`

``` cpp
struct NodeExpr {
    Token int_lit;
};
```

This structure represents an expression in our AST.

At the moment, our expression grammar only supports an integer literal,
such as `222`. The `int_lit` member stores the token representing that
integer.

Later, when the language supports expressions such as `10 + 20`, the
expression node will need to represent more than one integer token. The
current structure is intentionally limited.

## 2.4 AST node: `NodeExit`

``` cpp
struct NodeExit {
    NodeExpr expr;
};
```

This structure represents an exit statement. It contains a `NodeExpr`,
because the exit statement needs an expression whose value will become
the program's exit status.

The relationship is:

``` text
NodeExit
    |
    +-- expr: NodeExpr
              |
              +-- int_lit: Token
```

Keeping the expression as its own node gives the AST room to grow when
we add more expression types.

## 2.5 The Parser constructor

``` cpp
inline explicit Parser(vector<Token> tokens)
    : m_tokens(move(tokens))
{
}
```

This constructor receives the token vector. In `main.cpp`, we call:

``` cpp
Parser parser(move(tokens));
```

That passes the tokens produced by the Tokenizer into the Parser.

`move(tokens)` allows the vector's resources to be transferred into
`m_tokens` rather than copying all its elements. The Parser stores the
received tokens in:

``` cpp
const vector<Token> m_tokens;
```

`const` means the Parser will not modify the token vector itself. It can
still change its reading position using `m_index`.

## 2.6 `parse_expr()` --- parsing an expression

``` cpp
optional<NodeExpr> parse_expr() {
    if (peak().has_value() && peak().value().type == TokenType::int_lit) {
        return NodeExpr{.int_lit = consume()};
    } else {
        return {};
    }
}
```

This function tries to parse one expression. Our current expression rule
is:

``` text
expression -> integer_literal
```

### Why return `optional<NodeExpr>`?

The Parser may or may not find a valid expression at the current token
position.

-   It contains a `NodeExpr` when parsing succeeds.
-   It is empty when the current token cannot be parsed as an
    expression.

### Check whether a token is available

``` cpp
peak().has_value()
```

The `peak()` function returns an optional token. `.has_value()` checks
whether it contains a token.

### Check whether it is an integer literal

``` cpp
peak().value().type == TokenType::int_lit
```

`.value()` extracts the token from the optional. Then `.type` checks its
token type.

The `&&` operator matters: C++ evaluates the left side first and, if it
is false, does not evaluate the right side. Therefore, `.value()` is
reached only when a token is available.

### Construct the expression node

``` cpp
return NodeExpr{.int_lit = consume()};
```

If the token is an integer literal, `consume()` returns that token and
advances the Parser's position. The returned token is placed into a new
`NodeExpr`.

### If the token is not an integer literal

``` cpp
return {};
```

This returns an empty optional. It means this function could not parse
an expression at the current position. It does not itself print an error
or terminate the program.

## 2.7 `parse()` --- parsing the exit statement

``` cpp
optional<NodeExit> parse() {
    optional<NodeExit> exit_node;
```

This is the main parsing function. It returns an optional `NodeExit`:

-   A value means an exit AST node was constructed.
-   An empty optional means no exit node was returned.

The local variable `exit_node` stores the AST node after it has been
constructed.

### Loop while tokens remain

``` cpp
while (peak().has_value()) {
```

The loop continues while there is a token at the current position.

### Check for the `exit` keyword

``` cpp
if (peak().value().type == TokenType::exit) {
    consume();
```

The Parser looks at the current token. If it is the `exit` keyword, it
consumes it and advances.

### Parse the expression

``` cpp
if (auto node_expr = parse_expr()) {
    exit_node = NodeExit{.expr = node_expr.value()};
} else {
    cerr << "Invalid Expression !" << endl;
    exit(EXIT_FAILURE);
}
```

This is an `if` statement with an initializer:

1.  `parse_expr()` is called.
2.  Its optional result is stored in `node_expr`.
3.  The condition checks whether the optional contains a value.
4.  If it does, `node_expr.value()` extracts the `NodeExpr`.
5.  A `NodeExit` is constructed with that expression.

The initializer `NodeExit{.expr = node_expr.value()}` uses C++
designated initialization. It initializes the member named `expr`.

If expression parsing fails, the code prints an error and terminates
Hydro with `EXIT_FAILURE`.

### Check for the semicolon

``` cpp
if (peak().has_value() && peak().value().type == TokenType::semi) {
    consume();
} else {
    cerr << "Invalid Expression !" << endl;
    exit(EXIT_FAILURE);
}
```

After parsing the expression, the Parser expects a semicolon. If it is
present, `consume()` advances past it. Otherwise, the code reports an
error and terminates.

## 2.8 Reset the index and return

``` cpp
m_index = 0;
return exit_node;
```

`m_index` is reset to zero, so the Parser's reading position goes back
to the first token.

This reset is not required just to return the AST. It only makes sense
if we intentionally want to reuse the Parser's token-reading position
later.

The function then returns the optional AST node.

## 2.9 `peak()` --- look at a token without consuming it

``` cpp
inline optional<Token> peak(int ahead = 0) const {
    if (m_index + ahead >= m_tokens.size()) {
        return {};
    } else {
        return m_tokens[m_index + ahead];
    }
}
```

This is the Parser's look-ahead function. It is similar to the
character-reading function in the Tokenizer, but here it works with
`Token` objects instead of individual characters.

The parameter `int ahead = 0` has a default value of zero:

-   `peak()` looks at the current token.
-   `peak(1)` looks one token ahead.
-   `peak(2)` looks two tokens ahead.

It does not modify `m_index`.

Example:

``` text
Index:  0       1       2       3        4
Token:  exit    (       222     )        ;
```

If `m_index` is `2`:

  Call        Token returned   Does the index move?
  ----------- ---------------- ----------------------
  `peak()`    `222`            No
  `peak(1)`   `)`              No
  `peak(2)`   `;`              No

The boundary check `m_index + ahead >= m_tokens.size()` checks whether
the requested position is outside the vector. If it is, the function
returns an empty optional.

## 2.10 `consume()` --- take a token and advance

``` cpp
inline Token consume() {
    return m_tokens[m_index++];
}
```

This returns the token at the current position and increments `m_index`.

`m_index++` is post-increment:

1.  Use the old value of `m_index` to access the vector.
2.  Increment `m_index` afterwards.

If `m_index` is `2`, `consume()` returns the token at index `2` and
changes the index to `3`.

The difference:

-   `peak()` observes a token without advancing.
-   `consume()` returns the current token and advances.

## 2.11 Parser member variables

``` cpp
const vector<Token> m_tokens;
size_t m_index = 0;
```

`m_tokens` stores the tokens received by the Parser.

`m_index` stores the position of the next token to examine or consume.

`size_t` is an unsigned integer type commonly used for sizes and
container indexes.

## 2.12 Important limitations in this current Parser

The code shown is an early implementation, not a complete parser yet.

1.  **Opening parenthesis is not checked.** After consuming `exit`, the
    current code calls `parse_expr()` immediately. It does not verify
    that the next token is `(`.
2.  **Closing parenthesis is not checked.** After parsing the integer
    expression, it checks for `;` directly. It does not verify `)`.
3.  **Unexpected tokens can cause an infinite loop.** If the current
    token is not `exit`, the loop body does not consume anything or
    return an error. The same token can be examined repeatedly.
4.  **Only one exit node is stored.** `exit_node` is a single optional,
    so this structure does not represent a list of statements.
5.  **Error handling is basic.** `exit(EXIT_FAILURE)` terminates the
    whole compiler immediately rather than returning a structured
    parsing error.
6.  **Trailing tokens are not comprehensively rejected.** A complete
    parser should ensure the entire token sequence has been handled
    according to the grammar.

These are useful next improvements. They do not change what the current
functions are intended to teach.

# 3. `generation.hpp` --- converting the AST into assembly

The Generator receives the AST from the Parser and produces assembly
text.

The code we worked with is:

``` cpp
#pragma once
#include "./tokenization.hpp"
#include "./parser.hpp"

class Generator {
public:
    inline Generator(NodeExit root)
        : m_root(move(root))
    {
    }

    [[nodiscard]] string generate() const {
        stringstream output;
        output << "global _start\n_start:\n";
        output << "    mov rax, 60\n";
        output << "    mov rdi, " << m_root.expr.int_lit.value.value() << endl;
        output << "    syscall";
        return output.str();
    }

private:
    const NodeExit m_root;
};
```

## 3.1 Why include `parser.hpp`?

The Generator needs the AST node types defined by the Parser: `NodeExit`
and `NodeExpr`.

The Generator receives a `NodeExit` and reads the expression stored
inside it. It does not tokenize or parse the original source code again.

## 3.2 The Generator constructor

``` cpp
inline Generator(NodeExit root)
    : m_root(move(root))
{
}
```

The constructor receives the root AST node and stores it in:

``` cpp
const NodeExit m_root;
```

`move(root)` transfers the resources of the received object into
`m_root`.

## 3.3 The `generate()` function

``` cpp
[[nodiscard]] string generate() const
```

This function returns a `string` containing generated assembly.

-   `string` is the return type.
-   `generate` is the function name.
-   `const` means the function does not modify the Generator's member
    state.
-   `[[nodiscard]]` asks the compiler to warn if the returned value is
    ignored.

The Generator builds assembly in memory. It does not directly create
`out.asm`.

## 3.4 Create a string stream

``` cpp
stringstream output;
```

A `stringstream` lets us build a string piece by piece using `<<`.
Calling `.str()` later retrieves the combined string.

Here, the pieces are assembly instructions.

## 3.5 Generate the entry point

``` cpp
output << "global _start\n_start:\n";
```

This adds:

``` asm
global _start
_start:
```

`global _start` makes the `_start` symbol visible to the linker.

`_start:` defines an assembly label. In this simple Linux program, it is
the entry point where execution begins.

This is not a C++ `main()` function. We are generating a low-level
program that starts at `_start`.

The `\n` characters are newline characters.

## 3.6 Select the system call

``` cpp
output << "    mov rax, 60\n";
```

This generates:

``` asm
mov rax, 60
```

`mov` copies a value into a register.

For Linux x86-64, system call number `60` represents the `exit` system
call. The `rax` register holds the system call number.

## 3.7 Supply the exit status

``` cpp
output << "    mov rdi, " << m_root.expr.int_lit.value.value() << endl;
```

This line reads the integer value from the AST and inserts it into the
assembly text.

Follow the member access:

  Expression   Meaning
  ------------ -----------------------------------------
  `m_root`     The stored `NodeExit`
  `.expr`      Its `NodeExpr` member
  `.int_lit`   The integer-literal `Token`
  `.value`     The optional value stored in that token
  `.value()`   Extract the contained value

The exact type of `Token::value` comes from `tokenization.hpp`. In the
code shown, calling `.value()` means it is being treated as an
optional-like object.

If the source was `exit(222);`, the generated instruction becomes:

``` asm
mov rdi, 222
```

For the Linux x86-64 `exit` system call, `rdi` carries the first
argument: the exit status.

Therefore:

-   `rax = 60`: request the `exit` system call.
-   `rdi = 222`: provide exit status `222`.

`endl` adds a newline and flushes the output stream.

## 3.8 Invoke the system call

``` cpp
output << "    syscall";
```

This adds:

``` asm
syscall
```

The `syscall` instruction transfers control to the Linux kernel to
perform the system call selected in `rax`, using arguments in the
appropriate registers.

In this case, the process exits with the status supplied in `rdi`.

## 3.9 Return the assembly string

``` cpp
return output.str();
```

`.str()` retrieves all text accumulated in the stringstream.

For `exit(222);`, the returned string is:

``` asm
global _start
_start:
    mov rax, 60
    mov rdi, 222
    syscall
```

**The Generator returns assembly as a C++ string. `main.cpp` is
responsible for writing that string into `out.asm`.**

## 3.10 Store the AST

``` cpp
private:
    const NodeExit m_root;
```

The Generator keeps the AST root as a private member. It is `const`, so
the Generator's methods cannot modify the stored root through this
member.

The Generator needs this AST because `generate()` reads the integer
literal from it.

## 3.11 Current Generator limitation

The current Generator always emits the same exit-system-call sequence.
Only the value inserted into `rdi` changes.

It does not yet generate code for arithmetic, variables, conditions,
loops, functions, or multiple statement types. That is expected at this
stage.

# 4. `main.cpp` --- connecting all compiler components

`main.cpp` is the orchestration layer. It coordinates the work but does
not implement tokenization, parsing, or assembly generation itself.

The code we discussed is:

``` cpp
#include <bits/stdc++.h>
#include <fstream>
#include <sstream>
#include "./tokenization.hpp"
#include "./parser.hpp"
#include "./generation.hpp"

using namespace std;

int main(int argc, char* argv[]) {
    if (argc != 2) {
        cerr << "Incorrect usage. Correct Usage is..." << endl;
        cerr << "hydro <input.hy>" << endl;
        return EXIT_FAILURE;
    }

    string contents;
    {
        stringstream contents_stream;
        fstream input_file_content(argv[1], ios::in);
        contents_stream << input_file_content.rdbuf();
        contents = contents_stream.str();
    }

    Tokenizer tokenizer(move(contents));
    vector<Token> tokens = tokenizer.tokenize();

    Parser parser(move(tokens));
    optional<NodeExit> tree = parser.parse();

    if (!tree.has_value()) {
        cerr << "No Exit Statement Found" << endl;
        exit(EXIT_FAILURE);
    }

    Generator generator(tree.value());
    {
        fstream file("out.asm", ios::out);
        file << generator.generate();
    }

    system("nasm -felf64 out.asm");
    system("ld -o out out.o");

    return EXIT_SUCCESS;
}
```

## 4.1 Standard and project headers

``` cpp
#include <bits/stdc++.h>
#include <fstream>
#include <sstream>
#include "./tokenization.hpp"
#include "./parser.hpp"
#include "./generation.hpp"
```

-   `<bits/stdc++.h>` includes most standard C++ library headers. It is
    common in competitive programming but is not a standard portable
    header.
-   `<fstream>` provides file-stream classes such as `fstream`.
-   `<sstream>` provides string-stream classes such as `stringstream`.
-   `tokenization.hpp` provides the Tokenizer and Token definitions.
-   `parser.hpp` provides the Parser and AST definitions.
-   `generation.hpp` provides the Generator.

## 4.2 `using namespace std`

``` cpp
using namespace std;
```

This lets us write `string`, `vector`, `fstream`, `stringstream`, and
`cerr` instead of prefixing them with `std::`.

It is convenient in this small project. In larger projects, explicitly
qualifying names or using narrower `using` declarations can avoid naming
conflicts.

## 4.3 The `main()` arguments

``` cpp
int main(int argc, char* argv[]) {
```

`argc` is the number of command-line arguments. `argv` is an array of
C-style strings containing those arguments.

When running:

``` bash
./hydro program.hy
```

the typical values are:

  Expression   Meaning
  ------------ --------------
  `argc`       `2`
  `argv[0]`    `./hydro`
  `argv[1]`    `program.hy`

The executable name itself is counted as an argument.

## 4.4 Validate command-line usage

``` cpp
if (argc != 2) {
    cerr << "Incorrect usage. Correct Usage is..." << endl;
    cerr << "hydro <input.hy>" << endl;
    return EXIT_FAILURE;
}
```

Hydro expects exactly one command-line argument after the executable
name: the input file.

If the user supplies too few or too many arguments, the program prints
the expected usage and returns failure.

`cerr` is the standard error stream, appropriate for error messages.
`EXIT_FAILURE` indicates unsuccessful termination.

## 4.5 Read the source file into a string

``` cpp
string contents;
{
    stringstream contents_stream;
    fstream input_file_content(argv[1], ios::in);
    contents_stream << input_file_content.rdbuf();
    contents = contents_stream.str();
}
```

The Tokenizer receives source text, not a filename. Therefore,
`main.cpp` first reads the file into a string.

``` cpp
string contents;
```

This will hold the source code read from the `.hy` file.

``` cpp
stringstream contents_stream;
```

This stream accumulates the file contents.

``` cpp
fstream input_file_content(argv[1], ios::in);
```

`argv[1]` is the filename supplied by the user. `ios::in` opens the file
for reading.

``` cpp
contents_stream << input_file_content.rdbuf();
```

`rdbuf()` gives access to the file stream's underlying stream buffer.
Inserting that buffer into `contents_stream` copies the file's contents
into the string stream.

``` cpp
contents = contents_stream.str();
```

`.str()` returns the string accumulated in `contents_stream`.

The braces create a local scope. When execution leaves that scope, the
`stringstream` and `fstream` objects are destroyed and their resources
are released. The `contents` string remains alive because it was
declared outside the braces. This is an example of C++ object lifetime
and RAII.

**Current limitation:** the code does not check whether opening the
input file succeeded. If the filename is wrong or the file cannot be
opened, the program should report that instead of continuing with an
empty string.

## 4.6 Create the Tokenizer and tokenize the source

``` cpp
Tokenizer tokenizer(move(contents));
vector<Token> tokens = tokenizer.tokenize();
```

The first line constructs a Tokenizer and passes the source string to
it.

`move(contents)` transfers the string's resources to the Tokenizer.
`main()` does not need the original string afterwards.

The second line calls `tokenize()` and stores the returned tokens in a
vector.

The Tokenizer reads characters and recognizes tokens. The Parser
consumes this vector next.

## 4.7 Create the Parser and parse the tokens

``` cpp
Parser parser(move(tokens));
optional<NodeExit> tree = parser.parse();
```

The first line constructs a Parser and transfers the token vector into
it.

The second line calls `parse()`. The Parser checks the token sequence
according to its supported syntax and constructs an AST node.

`tree` is an `optional<NodeExit>` because parsing may not produce a
`NodeExit`.

The variable name `tree` is used for the AST result. Technically, the
current AST is a small structure rather than a general-purpose tree with
many node types.

## 4.8 Check the AST result

``` cpp
if (!tree.has_value()) {
    cerr << "No Exit Statement Found" << endl;
    exit(EXIT_FAILURE);
}
```

This checks whether the optional contains a `NodeExit`.

If it does not, the program reports that no exit statement was found and
terminates unsuccessfully.

`tree.value()` later extracts the contained `NodeExit`. It should only
be called after confirming that the optional contains a value.

## 4.9 Construct the Generator

``` cpp
Generator generator(tree.value());
```

The Generator receives the AST root. It can now inspect the parsed
expression and produce assembly.

The responsibilities are separate:

-   `main.cpp` passes the AST.
-   The Generator decides which assembly text to produce.
-   `main.cpp` decides where to save that text.

## 4.10 Save the generated assembly

``` cpp
{
    fstream file("out.asm", ios::out);
    file << generator.generate();
}
```

The Generator's `generate()` function returns a string containing
assembly.

`fstream` opens `out.asm` for writing. The insertion operator writes the
returned string into the file.

The file object is destroyed when the block ends, which closes the file
automatically.

The Generator does not create or open the file itself.

## 4.11 Run NASM

``` cpp
system("nasm -felf64 out.asm");
```

`system()` asks the operating system to execute the supplied shell
command.

-   `nasm` is the assembler.
-   `-felf64` selects the 64-bit ELF object-file format.
-   `out.asm` is the input assembly file.

The expected output is `out.o`.

This is an object file, not yet the final executable.

## 4.12 Run the linker

``` cpp
system("ld -o out out.o");
```

This runs the Linux linker.

-   `ld` is the linker.
-   `-o out` specifies the output filename.
-   `out.o` is the input object file.

The result is an executable named `out`.

The simple assembly program uses `_start` as its entry point and
directly invokes a Linux system call, so this example can be linked
directly without the usual C or C++ runtime startup code.

## 4.13 Return success

``` cpp
return EXIT_SUCCESS;
```

This reports that Hydro completed successfully.

Do not confuse this with the exit status of the generated AviLang
program:

-   Hydro's own return value can be `EXIT_SUCCESS`.
-   The generated program `out` can return `222`.

They are two different processes with two different exit statuses.

## 4.14 Important improvement: check external command results

The current code runs NASM and `ld` but ignores the return values from
`system()`.

If NASM fails, Hydro still attempts to run `ld`.

A later improvement should check whether each command succeeded and stop
compilation if a stage fails. Also, because `system()` invokes a shell,
a more robust compiler will eventually use safer process-execution APIs
and carefully handle filenames. For this learning stage, these commands
make the pipeline easy to see.

# 5. How the files work together

## 5.1 Tokenizer to Parser

In `main.cpp`:

``` cpp
Tokenizer tokenizer(move(contents));
vector<Token> tokens = tokenizer.tokenize();

Parser parser(move(tokens));
```

The Tokenizer returns a vector of tokens. That vector is passed to the
Parser constructor.

The Parser does not call the Tokenizer itself. `main.cpp` connects them.

## 5.2 Parser to Generator

In `main.cpp`:

``` cpp
optional<NodeExit> tree = parser.parse();

Generator generator(tree.value());
```

The Parser returns an AST node inside an optional. After checking that
the optional has a value, `main.cpp` extracts the AST and passes it to
the Generator.

The Parser does not call the Generator. `main.cpp` connects them.

## 5.3 Generator to output file

In `main.cpp`:

``` cpp
file << generator.generate();
```

The Generator returns assembly as a string. `main.cpp` writes that
string to `out.asm`.

The Generator does not create or open the file itself.

## 5.4 External tools

After `out.asm` is written:

``` cpp
system("nasm -felf64 out.asm");
system("ld -o out out.o");
```

NASM and `ld` are external programs, not C++ classes in our compiler.
Hydro launches them through `system()`.

# 6. Complete example: compiling `exit(222);`

Suppose `program.hy` contains:

``` text
exit(222);
```

You run:

``` bash
./hydro program.hy
```

### Stage 1: Read source

`main.cpp` reads `program.hy` into `contents`.

``` text
contents = "exit(222);"
```

### Stage 2: Tokenize

The Tokenizer recognizes the source's individual pieces:

``` text
exit
(
222
)
;
```

These are stored in `vector<Token>`.

### Stage 3: Parse

The Parser checks the supported syntax and creates:

``` text
NodeExit
    |
    +-- expr
          |
          +-- int_lit: 222
```

### Stage 4: Generate

The Generator reads the integer literal from the AST and returns:

``` asm
global _start
_start:
    mov rax, 60
    mov rdi, 222
    syscall
```

### Stage 5: Save assembly

`main.cpp` writes the returned string into `out.asm`.

### Stage 6: Assemble

NASM converts:

``` text
out.asm -> out.o
```

### Stage 7: Link

The linker converts:

``` text
out.o -> out
```

### Stage 8: Execute

Run:

``` bash
./out
echo $?
```

The expected exit status is:

``` text
222
```

# 7. Important concepts from Day 2

  Concept          Meaning in our compiler
  ---------------- --------------------------------------------------
  Token            A recognized piece of source code
  Grammar          Rules describing valid token arrangements
  Parser           Checks syntax and constructs AST nodes
  AST              Structured representation of the program
  `NodeExpr`       Represents the expression supported currently
  `NodeExit`       Represents the exit statement
  `optional<T>`    Represents a value that may be absent
  `peak()`         Looks at a token without advancing
  `consume()`      Returns the current token and advances
  Generator        Converts AST structure into assembly text
  `stringstream`   Builds a string piece by piece
  Assembly         Human-readable low-level instructions
  Assembler        Converts assembly into an object file
  Object file      Machine code plus information used by the linker
  Linker           Produces the final executable from object files

## The three most important responsibilities

**Tokenizer:** What are the individual pieces?

**Parser:** Do those pieces form valid syntax, and what is their
structure?

**Generator:** Given that structure, what assembly instructions should
be produced?

# 8. Current limitations and what comes next

At this point, Hydro supports a very small language.

Current supported example:

``` text
exit(222);
```

The current code does not yet support:

-   Arithmetic expressions such as `10 + 20`.
-   Variables.
-   Multiple statement types.
-   Conditions such as `if`.
-   Loops.
-   Functions.
-   Semantic analysis and type checking.
-   A general AST capable of representing a complete program.

The Parser also needs stronger syntax checks for the opening and closing
parentheses, unexpected tokens, and multiple statements.

These are natural next steps. The purpose of this stage was to
understand the complete path from source text to a generated executable.

# 9. Day 2 recap

Today, we connected the components of Hydro:

1.  `main.cpp` reads the `.hy` file.
2.  The Tokenizer turns source characters into tokens.
3.  The Parser checks token arrangement and creates an AST.
4.  The Generator reads the AST and returns assembly as a string.
5.  `main.cpp` writes that string to `out.asm`.
6.  NASM assembles `out.asm` into `out.o`.
7.  `ld` links `out.o` into the executable `out`.

The biggest achievement is that Hydro is no longer just reading source
code or printing tokens. It now has a basic pipeline that can turn a
small AviLang program into a native Linux executable.

**The key mental model:** each stage receives one representation of the
program, performs one job, and passes a new representation to the next
stage.

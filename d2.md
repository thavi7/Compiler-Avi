# AviLang — Day 2 Notes

## Goal of Day 2

On Day 1, we made Hydro read an AviLang source file and tokenize its contents. On Day 2, we started connecting the next stages of the compiler:

- **Parser** — checks whether the sequence of tokens follows our language grammar.
- **AST (Abstract Syntax Tree)** — represents the structure of the program.
- **Code generator** — turns the parsed program into assembly.
- **Assembler and linker** — turn the generated assembly into an executable.

The goal was to move from merely recognizing tokens to generating a program that Linux can execute.

Our small language is still very limited. For now, we are working toward a statement like:

```text
exit(222);
```

The integer can change, but the basic grammar is:

```text
exit(<integer>);
```

# 2. Changing the Language Grammar

The earlier example was:

```text
return 222;
```

For Day 2, we started changing the language to use an `exit` statement with parentheses:

```text
exit(222);
```

The grammar we are trying to support is:

```text
[exit] → exit([expr]);

[expr] → int_lit
```

These rules describe the structure that the parser expects.

## What does the first rule mean?

```text
[exit] → exit([expr]);
```

A valid exit statement must contain:

1. The `exit` keyword.
2. An opening parenthesis `(`.
3. An expression.
4. A closing parenthesis `)`.
5. A semicolon `;`.

For example:

```text
exit(222);
```

is the intended shape.

## What does the expression rule mean?

```text
[expr] → int_lit
```

For now, an expression is just an integer literal.

Examples:

```text
exit(0);
exit(1);
exit(222);
```

At this stage, expressions such as these are not supported by this grammar:

```text
exit(10 + 5);
exit(20 - 3);
```

We have not added arithmetic expression parsing yet.

---

# 3. What Is a Parser?

A **parser** takes the tokens produced by the lexer and checks how they fit together according to the language grammar.

The lexer answers:

> What individual pieces are present in the source code?

The parser answers:

> Are those pieces arranged in a valid program structure?

For example, the source:

```text
exit(222);
```

may be tokenized into a sequence representing:

```text
exit
(
222
)
;
```

The parser checks that these tokens appear in the expected order.

A source file can contain recognizable tokens but still have invalid syntax. For example:

```text
exit(222
```

is missing the closing parenthesis and semicolon. A parser is responsible for detecting that kind of structural error.

---

# 4. Why the Parser Needs the Tokens

The parser receives the token vector created by the tokenizer.

Conceptually:

```cpp
Parser parser(move(tokens));
```

Here, `tokens` is passed to the parser. `move(tokens)` allows the vector's resources to be transferred instead of copying the entire vector.

The parser keeps the tokens so it can examine them in order.

The parser does not need to re-read the original source file. That work has already been done by the earlier stages.

---

# 5. The AST — Abstract Syntax Tree

An **AST** is a structured representation of the program after parsing.

Instead of making later compiler stages work directly with a flat sequence of tokens, we represent the program in terms of nodes.

For our current grammar, the structure is conceptually:

```text
NodeExit
   |
   └── NodeExpr
          |
          └── int_lit: "222"
```

The exact C++ member names depend on the structs in our implementation, but the relationship is what matters.

## `NodeExpr`

An expression node represents the expression inside the exit statement.

Since the only supported expression is an integer literal, it can contain the integer-literal token.

Conceptually:

```cpp
struct NodeExpr {
    Token int_lit;
};
```

## `NodeExit`

An exit node represents the complete exit statement. It contains the expression that determines the exit status.

Conceptually:

```cpp
struct NodeExit {
    NodeExpr expr;
};
```

This creates a relationship:

```text
NodeExit
   ↓
NodeExpr
   ↓
Token containing the integer literal
```

For `exit(222);`, the AST stores the value represented by the `222` token.

## Why not store a `NodeExpr` inside itself?

An incorrect structure would be:

```cpp
struct NodeExpr {
    NodeExpr expr;
};
```

This makes a `NodeExpr` contain another complete `NodeExpr`, which would contain another one, indefinitely. C++ cannot determine a finite size for that object.

Instead, our current expression node stores a `Token`, because the only expression supported so far is an integer literal.

---

# 6. `optional` and Parsing Failure

The parser uses `optional` to represent a result that may or may not exist.

Conceptually:

```cpp
optional<NodeExpr> parse_expr();
```

This means:

- A `NodeExpr` is returned if the next token is a supported expression.
- An empty `optional` is returned if the next token does not match an expression.

For the current grammar:

```text
int_lit
```

is the only valid expression.

So if the next token is an integer literal, `parse_expr()` can create an expression node. If the next token is something else, the expression cannot be parsed.

Similarly:

```cpp
optional<NodeExit> parse();
```

allows the parser to report that it could not produce an exit-statement AST.

`optional` is not itself an error message. It is a way to represent the presence or absence of a value. The parser or the caller still needs to decide how to report invalid syntax.

---

# 7. Looking at Tokens: `peek()` and `consume()`

A parser commonly needs two small operations.

## `peek()`

`peek()` looks at the next token without moving past it.

For example, if the next token is an integer literal, `peek()` lets the parser check its type before deciding what to do.

The parser can also check whether a token exists. If the index is already at the end of the vector, there is no next token.

## `consume()`

`consume()` returns the current token and advances the token index.

Conceptually:

```text
Before:
index → exit  (  222  )  ;

After consuming exit:
        exit  (  222  )  ;
index →       (
```

This is important: every successful parsing step must advance through the expected tokens.

## Why do we need both?

We often want to inspect a token before consuming it.

For example:

1. Check whether the next token is `exit`.
2. Consume `exit`.
3. Check and consume `(`.
4. Parse the expression.
5. Check and consume `)`.
6. Check and consume `;`.

The parser should not consume a token merely because one exists. It should consume it only when it matches the grammar rule it is currently parsing.

---

# 8. Parsing the Complete Exit Statement

For the grammar:

```text
[exit] → exit([expr]);
```

the parser needs to follow this order:

```text
Check for exit
      ↓
Consume exit
      ↓
Check for (
      ↓
Consume (
      ↓
Parse expression
      ↓
Check for )
      ↓
Consume )
      ↓
Check for ;
      ↓
Consume ;
      ↓
Build NodeExit
```

Each check matters. If the parser skips the parentheses, it may attempt to parse the `(` token as an integer expression and fail.

The semicolon check also needs to confirm that a token exists **and** that its type is `semi`. A condition that only checks whether some token exists does not prove that the token is a semicolon.

After the statement has been parsed, the parser should also consider whether any unexpected tokens remain. Otherwise, invalid trailing input could go unnoticed.

---

# 9. `NodeExit` and `NodeExpr` Must Agree

When creating an AST node, the field name used in the initializer must match a field declared in the struct.

For example, if the struct is:

```cpp
struct NodeExit {
    NodeExpr expr;
};
```

then its member is named `expr`. An initializer using `.exit` would fail because `NodeExit` has no member called `exit`.

The same rule applies when the code generator reads the AST. If `NodeExit` contains `expr`, the generator should access that member and then access the integer-literal token inside the expression.

The structure should be consistent from parsing through code generation:

```text
Parser creates NodeExit
        ↓
NodeExit contains NodeExpr
        ↓
NodeExpr contains the integer-literal Token
        ↓
Generator reads that integer value
```

---

# 10. Generating Assembly from the AST

After parsing, the generator receives the AST instead of needing to interpret the original source text again.

The goal is to produce assembly that performs the equivalent of:

```cpp
exit(222);
```

For Linux x86-64, the generated assembly can look like:

```asm
global _start
_start:
    mov rax, 60
    mov rdi, 222
    syscall
```

The value `222` is an example. The generator should use the integer literal stored in the AST.

## What each instruction does

### `global _start`

Makes the `_start` symbol visible to the linker as an entry-point symbol.

### `_start:`

Marks the entry point where execution begins.

### `mov rax, 60`

Places the Linux x86-64 system-call number for `exit` into `rax`.

Here, `60` identifies the operation. It is not the program's exit status.

### `mov rdi, 222`

Places the exit status into `rdi`.

In this example, the program requests an exit status of `222`.

### `syscall`

Asks the Linux kernel to perform the system call using the values in the registers.

Conceptually, these instructions perform the equivalent of:

```cpp
exit(222);
```

---

# 11. Why the Generator Needs the AST

The generator should not hardcode the exit status as `222`.

Instead, it reads the integer literal from the AST.

For example, if the source is:

```text
exit(5);
```

the generated assembly should use:

```asm
mov rdi, 5
```

If the source is:

```text
exit(222);
```

the generated assembly should use:

```asm
mov rdi, 222
```

This is the point of connecting the parser to the generator: the output depends on the source program that was parsed.

In our current design, the generator stores the root `NodeExit` and produces an assembly string, which can then be written to a file.

---

# 12. `stringstream` in the Generator

The generator uses a string stream to build the assembly text.

Instead of writing each instruction directly to a file, it can append the instructions to a `stringstream` and return the result as a normal string.

The flow is:

```text
AST
 ↓
Generator
 ↓
stringstream
 ↓
Assembly string
 ↓
out.asm
```

The main program then writes the returned string to `out.asm`.

This separates the job of **creating assembly text** from the job of **writing that text to a file**.

---

# 13. From `out.asm` to an Executable

After the generator writes the assembly, the compiler invokes NASM and the linker.

The commands used in our current workflow are:

```bash
nasm -felf64 out.asm
ld -o out out.o
```

## Step 1: NASM

```bash
nasm -felf64 out.asm
```

NASM assembles the x86-64 assembly source into an object file:

```text
out.o
```

The `-felf64` option selects the 64-bit ELF object-file format used by our Linux toolchain.

## Step 2: Linker

```bash
ld -o out out.o
```

The linker takes `out.o` and produces an executable named:

```text
out
```

The complete process is:

```text
out.asm
   ↓
 NASM
   ↓
 out.o
   ↓
  ld
   ↓
  out
```

This is the same assembler-and-linker pipeline we experimented with on Day 1, but now Hydro generates the assembly from the source program.

---

# 14. How `main.cpp` Connects the Stages

The main program coordinates the compiler pipeline.

The overall order is:

1. Check the command-line arguments.
2. Open the source file specified by the user.
3. Read the file into a string.
4. Pass the source string to the tokenizer.
5. Get the token vector.
6. Pass the tokens to the parser.
7. Get the AST, or report that parsing failed.
8. Pass the AST to the generator.
9. Write the generated assembly to `out.asm`.
10. Run NASM to create `out.o`.
11. Run `ld` to create the executable `out`.

The high-level flow is:

```text
./build/hydro test.hy
          ↓
       main.cpp
          ↓
    Read test.hy
          ↓
       Tokenizer
          ↓
        tokens
          ↓
        Parser
          ↓
         AST
          ↓
       Generator
          ↓
        out.asm
          ↓
         NASM
          ↓
         out.o
          ↓
          ld
          ↓
          out
```

Each stage has a distinct responsibility. This makes the compiler easier to understand and extend.

# 15. Errors We Encountered While Building the Parser

While writing the parser and generator, we ran into several C++ errors. These were useful because they showed how the AST structure and parser logic must fit together.

## A. Missing semicolon after a class

A C++ class definition ends with:

```cpp
};
```

not just:

```cpp
}
```

The semicolon is required after the closing brace of a class or struct definition.

## B. Initializing a field that does not exist

If a struct declares a member named `expr`, an initializer such as `.exit = ...` is invalid.

The initializer must use the actual member name declared in the struct.

## C. Recursive object stored by value

A struct cannot contain a complete object of its own type as a direct data member:

```cpp
struct NodeExpr {
    NodeExpr expr;
};
```

That would require an infinitely sized object. Our current `NodeExpr` can store the integer-literal `Token` instead.

## D. Calling `value()` on the wrong expression

When `peak` is a function, the call is:

```cpp
peak()
```

To access the optional result's value, the function must first be called, and then the optional's `value()` can be used.

## E. Incorrect `if` initialization syntax

An `if` statement that initializes a variable uses `=`:

```cpp
if (auto node_expr = parse_expr()) {
}
```

Using `==` there is not a valid declaration-and-initialization.

## F. Checking a token type incorrectly

A token type is an enum value, not a boolean. To check for a semicolon, compare it explicitly with the semicolon token type.

The parser must also make sure a token exists before accessing it.

## G. Misspelled names and missing semicolons

Errors such as misspelling `return`, misspelling `EXIT_FAILURE`, or leaving off a semicolon after a statement can prevent compilation. C++ compiler diagnostics point to the location where the parser could no longer understand the code, though the original mistake can sometimes be on the preceding line.

## H. Extra colon in the constructor initializer list

A constructor initializer list uses one colon:

```cpp
Generator(NodeExit root)
    : m_root(move(root)) {
}
```

An additional colon before `m_root` is invalid syntax.

# 16. Important Parser Logic Lessons

A compiler can compile successfully while still having incorrect parsing logic. We therefore need to check both syntax and behavior.

## Always advance through the input

If a parsing loop sees a token it does not handle and never consumes it or reports an error, the loop can become stuck on the same token.

A parser should either:

- consume a token that belongs to the construct being parsed, or
- report that the input is invalid.

## Check the expected token, not just whether a token exists

For example, after parsing the expression, the next token must be the closing parenthesis. The fact that a token exists is not enough.

The same applies to the semicolon.

## Match the grammar in order

For `exit(222);`, parsing the integer immediately after `exit` is incorrect because the next token is the opening parenthesis.

The parser must handle the punctuation in the grammar as well as the expression.

## Do not assume parsing succeeded

If the parser returns an empty `optional`, the main program should stop with a failure message instead of passing a nonexistent AST to the generator.

# 17. Testing the Compiler

A simple source file for the current grammar is:

```text
exit(222);
```

The goal is for Hydro to parse it, generate assembly, assemble it, and link the executable.

From the project root, build Hydro:

```bash
cmake --build build
```

Then run it with the source file:

```bash
./build/hydro test.hy
```

The precise relative path depends on the directory where the command is run. If the terminal is already inside `build/`, the source file in the project root may be referenced as:

```bash
./hydro ../test.hy
```

After Hydro runs successfully, inspect the generated assembly:

```bash
cat out.asm
```

It should contain the exit system-call instructions, with the integer taken from the source program.

Then run the generated executable:

```bash
./out
```

To inspect the exit status in Bash, immediately run:

```bash
echo $?
```

For the example `exit(222);`, the expected status is `222`.

Remember that an exit status is a small integer reported to the operating system; it is not normal text printed to the terminal.

# 19. What Is Not Supported Yet?

Our language is still intentionally small.

The current grammar only describes an exit statement whose expression is an integer literal:

```text
exit(<integer>);
```

We have not yet built:

- Arithmetic expressions such as `10 + 5`.
- Variables and identifiers.
- Multiple statement types.
- Semantic analysis.
- An intermediate representation (IR).
- Rich error messages with source locations.
- A robust mechanism for reporting failures from the NASM and linker commands.

These can be introduced incrementally as the language grows.

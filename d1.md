## Goal of Day 1

Today we started understanding the basic tools and concepts needed to build **AviLang**, our own programming language and compiler.

# 1. What Is a Compiler?

A compiler is a program that takes source code written in one programming language and translates it into something the computer can execute.

For AviLang, the eventual flow will look like:

```text
AviLang source code
        ↓
      Lexer
        ↓
     Tokens
        ↓
      Parser
        ↓
       AST
        ↓
Semantic Analysis
        ↓
       IR
        ↓
 Code Generation
        ↓
    Assembly
        ↓
 Machine Code / Object File
        ↓
     Linker
        ↓
   Executable
```

We are only at the very beginning of this pipeline.

# 2. CMake

CMake is a **build-system generator**.

It helps us tell the build tools:

- which source files belong to our program
- what executable to create
- how the project should be built

For example, our project can have:

```text
Compiler/
├── CMakeLists.txt
├── src/
│   └── main.cpp
├── build/
└── test.hy
```

`CMakeLists.txt` contains the instructions for CMake.

## Source directory vs build directory

The project root is:

```text
Compiler/
```

The source code is inside:

```text

```

The generated build files and executable are inside:

```text

```

We normally do not put AviLang source programs such as `test.hy` inside `build/`.


# 6. Understanding the Assembly Example

We do NOT need to become assembly experts right now.

The important concepts are enough for now.

## Registers

A register is a very small storage location inside the CPU.

Examples:

```text
rax
rdi
rsp
rbp
```

You can think of registers somewhat like variables, except they are part of the CPU and have special purposes.

## `mov`

This instruction copies/places a value into a register.

For example:

```asm
mov rax, 60
```

means approximately:

```text
rax = 60
```

And:

```asm
mov rdi, 222
```

means:

```text
rdi = 222
```

## `rax`

For Linux x86-64 system calls, `rax` contains the **system call number**.

In our example:

```text
rax = 60
```

System call number `60` means:

```text
exit
```

So `60` is NOT the value being returned.

It tells Linux:

> Perform the `exit` operation.

## `rdi`

For this system call, `rdi` contains the argument.

We have:

```text
rdi = 222
```

So Linux interprets the request as:

```text
exit(222)
```

## `syscall`

```asm
syscall
```

asks the operating system's kernel to perform the system call prepared in the registers.

So:

```asm
mov rax, 60
mov rdi, 222
syscall
```

is conceptually similar to:

```cpp
exit(222);
```

The important distinction:

```text
rax = 60
→ tells Linux WHAT operation to perform

rdi = 222
→ gives the argument to that operation

syscall
→ asks Linux to perform it
```

We only need this level of understanding for now.

# 14. `stringstream`

We used:

# 16. First Lexer

This was the biggest compiler concept we started today.

A **lexer** (also called a tokenizer) takes raw source code and breaks it into meaningful pieces called **tokens**.

Suppose our language has:

```text
return 222;
```

The lexer should recognize:

```text
return
222
;
```

and convert them into tokens:

```text
_return
int_lit("222")
semi
```

# 17. `TokenType`

We created:

```cpp
enum class TokenType {
    _return,
    int_lit,
    semi
};
```

This defines the types of tokens our language currently understands.

Currently:

```text
_return → the keyword "return"

int_lit → an integer literal such as 123

semi → the semicolon ;
```

This list will grow as AviLang gets more language features.

For example, later we may have tokens for:

```text
identifier
plus
minus
equal
left_paren
right_paren
```

and many others.

# 18. What Is a Token?

A token is a structured representation of something meaningful in source code.

We created:

```cpp
struct Token {
    TokenType type;
    optional<string> value{};
};
```

A token has:

```text
type
+
optional value
```

For example:

```text
222
```

can become:

```text
type  = int_lit
value = "222"
```

But:

```text
return
```

does not need a value:

```text
type  = _return
value = empty
```

And:

```text
;
```

can be:

```text
type = semi
value = empty
```

---

# 19. `optional<string>`

We used:

```cpp
optional<string> value{};
```

`optional` means the value may or may not exist.

For example:

```text
int_lit("222")
```

has a value.

But:

```text
_return
```

does not need one.

So `optional<string>` lets a token represent both situations.

# 20. `tokenize()`

We created:

```cpp
vector<Token> tokenize(string &str)
```

This function:

1. Receives the source code as a string.
2. Scans through it character by character.
3. Identifies keywords.
4. Identifies integer literals.
5. Identifies semicolons.
6. Creates `Token` objects.
7. Returns a `vector<Token>`.

The general flow is:

```text
source string
     ↓
tokenize()
     ↓
vector<Token>
```

# 21. How the Lexer Recognizes `return`

The lexer checks:

```cpp
if(isalpha(c))
```

`isalpha()` checks whether a character is an alphabetic letter.

It builds a temporary string:

```text
buf
```

For:

```text
return
```

it collects:

```text
r
re
ret
retu
retur
return
```

Then it checks:

```cpp
if(buf == "return")
```

If true, it creates:

```text
TokenType::_return
```

This is how the lexer recognizes a keyword.

---

# 22. How the Lexer Recognizes Numbers

The lexer checks:

```cpp
isdigit(c)
```

`isdigit()` checks whether a character is a digit.

For:

```text
222
```

it collects:

```text
2
22
222
```

Then it creates:

```text
TokenType::int_lit
```

and stores:

```text
"222"
```

as the token's value.

So:

```text
222
```

becomes:

```text
int_lit("222")
```

---

# 23. How the Lexer Recognizes `;`

The lexer checks:

```cpp
else if(c == ';')
```

If it finds `;`, it creates:

```text
TokenType::semi
```

So:

```text
;
```

becomes:

```text
semi
```

---

# 24. Whitespace

The lexer checks:

```cpp
isspace(c)
```

Whitespace includes things such as:

```text
space
tab
newline
```

Whitespace usually separates tokens but is not itself a meaningful token for our current language.

So:

```text
return     222;
```

can still be interpreted as:

```text
_return
int_lit("222")
semi
```

# Hydro Compiler — Day 1 (Part 2)

This file continues directly from `day1.md`. Day 1 ended with a working lexer.
Part 2 is about turning those tokens into **real assembly**, and then into a **real executable**.

---

## 28. New function: `tokens_to_asm()`

Day 1 gave us tokens. Tokens are useless on their own — something has to turn
them into instructions the CPU understands. That is this function's job:

```cpp
string tokens_to_asm(vector<Token>& tokens)
```

It takes the token vector produced by `tokenize()` and returns a `string`
containing **x86-64 assembly**.

We pass by reference (`&`) so the whole vector isn't copied.

---

## 29. The one pattern Hydro understands

Hydro currently recognizes exactly one sequence of tokens:

```
_return
int_lit
semi
```

which is what the lexer produces for:

```
return 222;
```

So when Hydro walks the token list and sees `_return`, it looks ahead:
is the next token an `int_lit`? Is the one after that a `semi`? If yes, it
emits assembly for it.

This is our first taste of **parsing**: looking at a *sequence* of tokens and
recognizing a meaningful structure, instead of looking at one token at a time.

---

## 30. The assembly we generate (and why)

For `return 222;` Hydro produces:

```asm
global _start
_start:
    mov rax, 60
    mov rdi, 222
    syscall
```

Line by line:

- `global _start` — makes the symbol `_start` visible to the linker.
- `_start:` — the **entry point**. `ld` starts execution here by default.
  (In C that job belongs to `main`, but `main` is a C convention; at the raw
  level the entry point is `_start`.)
- `mov rax, 60` — on Linux x86-64, you ask the kernel to do something by putting
  a **syscall number** in `rax`. **60 is the number for `exit`.** So this line
  means "the thing I want the kernel to do is: exit".
- `mov rdi, 222` — syscall **arguments** go in a fixed order of registers:
  `rdi`, `rsi`, `rdx`, ... So `rdi` is the *first* argument. `exit` takes one
  argument — the exit code. That's where our integer literal `222` goes.
- `syscall` — actually hands control to the kernel.

So `return 222;` in our language becomes "exit the process with status 222".
You can verify it after running the program:

```
./out
echo $?
```

which prints `222`.

---

## 31. Getting the number out: `tokens[i+1].value.value()`

Our `Token` struct stores its value as an `optional<string>`, because only some
tokens carry a value (`int_lit` does, `semi` does not).

```cpp
tokens[i + 1].value.value()
```

Read it as two separate `.value`s:

- the first `.value` is the **struct member** — the `optional<string>` itself.
- the second `.value()` is the **optional's method** — it unwraps the optional
  and gives you the actual `string` inside.

So this expression gives us `"222"` as a `string`, ready to paste into the
assembly. Calling `.value()` on an empty optional throws, which is why we only
call it after confirming the token really is an `int_lit`.

---

## 32. `stringstream output`

We are building up assembly line by line. Repeatedly concatenating with `+` is
clumsy, so we use a stream:

```cpp
stringstream output;
output << "global _start\n_start:\n";
```

`stringstream` behaves like `cout`, except it writes into memory instead of the
terminal. When we're done we pull the whole thing out as a string:

```cpp
return output.str();
```

---

## 33. Writing the assembly to a file

A string in memory is no good to NASM — it needs a real file on disk:

```cpp
fstream file("out.asm", ios::out);
file << tokens_to_asm(tokens);
```

- `ios::out` opens the file for writing (creating it, or truncating it if it exists).
- `file << ...` writes exactly like `cout << ...`.

After this line, `out.asm` exists on disk with our generated assembly in it.

---

## 34. What `system()` does

```cpp
system("command");
```

`system()` runs a **shell command** from inside a C++ program, exactly as if you
had typed it into the terminal yourself. It waits for the command to finish
before continuing.

This is how Hydro is going to drive tools it doesn't implement itself. We are
not writing an assembler or a linker today — we're borrowing NASM and `ld`.

---

## 35. Calling NASM: `out.asm → out.o`

```cpp
system("nasm -felf64 out.asm");
```

NASM is an **assembler**: it turns human-readable assembly text into machine
code in an object file.

- `-felf64` sets the output format to 64-bit ELF, which is the object/executable
  format Linux uses.
- The output is `out.o`.

So Hydro is now invoking another program as part of its own compilation process.
Real compilers do this constantly.

---

## 36. Calling the linker: `out.o → out`

```cpp
system("ld -o out out.o");
```

`ld` is the **linker**. It takes the object file, resolves addresses, sets up the
entry point (`_start`), and produces a finished executable.

- `-o out` names the output file `out`.
- The result, `out`, is a real program you can run with `./out`.

Notice this is the **same object-file-then-linker shape** as point 34 — the one
GCC uses internally when it builds Hydro itself.

---

## 37. The new full pipeline

```
test.hy
   ↓
Hydro
   ↓
tokenize()
   ↓
tokens
   ↓
tokens_to_asm()
   ↓
out.asm
   ↓
NASM
   ↓
out.o
   ↓
ld
   ↓
out   (executable)
```

The first four arrows are **our code**. The last two are **borrowed tools**.

## 38. Who is who — the file glossary

Six filenames, six different roles. Keep them straight:

| File | What it is |
|---|---|
| `main.cpp` | source code of Hydro |
| `hydro` | the executable compiler (built from `main.cpp`) |
| `test.hy` | the input program, written in our language |
| `out.asm` | the assembly Hydro generated from `test.hy` |
| `out.o` | object file produced by NASM |
| `out` | final executable produced by `ld` |

`hydro` is *our tool*. `out` is *the user's program*. They are completely
different executables.

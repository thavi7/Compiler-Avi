A compiler is a program that takes source code written in one programming language and translates it into something the computer can execute.

For AviLang, the eventual flow will look like:

```text
AviLang source code
        ↓
      Lexer
        ↓
     Tokens
        ↓
      Parser
        ↓
       AST
        ↓

        ↓
       IR
        ↓
 Code Generation
        ↓
    Assembly
        ↓

        ↓
     Linker
        ↓
   Executable
```

We are only at the very beginning of this pipeline.

# 2. CMake

## What is CMake?

CMake is a **build-system generator**.

It helps us tell the build tools:

- which source files belong to our program
- what executable to create
- how the project should be built

For example, our project can have:

```text
Compiler/
├── CMakeLists.txt
├── src/
│   └── main.cpp
├── build/
└── test.hy
```

`CMakeLists.txt` contains the instructions for CMake.

## Source directory vs build directory

The project root is:

```text
Compiler/
```

The source code is inside:

```text
src/
```

The generated build files and executable are inside:

```text
build/
```

We normally do not put AviLang source programs such as `test.hy` inside `build/`.

A good structure is:

```text
Compiler/
├── CMakeLists.txt
├── src/
│   └── main.cpp
├── build/
│   └── hydro
└── test.hy
```

## Important CMake commands

From the project root:

```bash
cmake -S . -B build
```

This means:

- `-S .` → use the current directory as the source/project directory
- `-B build` → put generated build files in `build`

Then:

```bash
cmake --build build
```

This builds the project.

The executable created by our CMake configuration is:

```text
build/hydro
```

So we can run it with:

```bash
./build/hydro
```

If we are already inside `build/`, we can run:

```bash
./hydro
```

# 6. Understanding the Assembly Example

We do NOT need to become assembly experts right now.

The important concepts are enough for now.

## Registers

A register is a very small storage location inside the CPU.

Examples:

```text
rax
rdi
rsp
rbp
```

You can think of registers somewhat like variables, except they are part of the CPU and have special purposes.

## `mov`

This instruction copies/places a value into a register.

For example:

```asm
mov rax, 60
```

means approximately:

```text
rax = 60
```

And:

```asm
mov rdi, 222
```

means:

```text
rdi = 222
```

## `rax`

For Linux x86-64 system calls, `rax` contains the **system call number**.

In our example:

```text
rax = 60
```

System call number `60` means:

```text
exit
```

So `60` is NOT the value being returned.

It tells Linux:

> Perform the `exit` operation.

## `rdi`

For this system call, `rdi` contains the argument.

We have:

```text
rdi = 222
```

So Linux interprets the request as:

```text
exit(222)
```

## `syscall`

```asm
syscall
```

asks the operating system's kernel to perform the system call prepared in the registers.

So:

```asm
mov rax, 60
mov rdi, 222
syscall
```

is conceptually similar to:

```cpp
exit(222);
```

The important distinction:

```text
rax = 60
→ tells Linux WHAT operation to perform

rdi = 222
→ gives the argument to that operation

syscall
→ asks Linux to perform it
```

We only need this level of understanding for now.

# 16. First Lexer

This was the biggest compiler concept we started today.

A **lexer** (also called a tokenizer) takes raw source code and breaks it into meaningful pieces called **tokens**.

Suppose our language has:

```text

```

The lexer should recognize:

```text

;
```

and convert them into tokens:

```text

```

Currently:

# 18. What Is a Token?

A token is a structured representation of something meaningful in source code.

We created:

```cpp
struct Token {
    TokenType type;
    optional<string> value{};
};
```

A token has:

```text
type
+
optional value
```

For example:

```text
222
```

can become:

```text
type  = int_lit
value = "222"
```

But:

```text
return
```

does not need a value:

```text
type  = _return
value = empty
```

And:

```text
;
```

can be:

```text
type = semi
value = empty
```

---

# 19. `optional<string>`

We used:

```cpp
optional<string> value{};
```

`optional` means the value may or may not exist.

For example:

```text
int_lit("222")
```

has a value.

But:

```text
_return
```

does not need one.

So `optional<string>` lets a token represent both situations.

# 20. `tokenize()`

We created:

```cpp
vector<Token> tokenize(string &str)
```

This function:

1. Receives the source code as a string.
2. Scans through it character by character.
3. Identifies keywords.
4. Identifies integer literals.
5. Identifies semicolons.
6. Creates `Token` objects.
7. Returns a `vector<Token>`.

The general flow is:

```text
source string
     ↓

     ↓
vector<Token>
```

# 21. How the Lexer Recognizes `return`

The lexer checks:

```cpp
if(isalpha(c))
```

`isalpha()` checks whether a character is an alphabetic letter.

It builds a temporary string:

```text
buf
```

For:

```text
return
```

it collects:

```text
r
re
ret
retu
retur
return
```

Then it checks:

```cpp
if(buf == "return")
```

If true, it creates:

```text
TokenType::_return
```

This is how the lexer recognizes a keyword.

---

# 22. How the Lexer Recognizes Numbers

The lexer checks:

```cpp
isdigit(c)
```

`isdigit()` checks whether a character is a digit.

For:

```text
222
```

it collects:

```text
2
22
222
```

Then it creates:

```text
TokenType::int_lit
```

and stores:

```text
"222"
```

as the token's value.

So:

```text
222
```

becomes:

```text
int_lit("222")
```

---

# 23. How the Lexer Recognizes `;`

The lexer checks:

```cpp
else if(c == ';')
```

If it finds `;`, it creates:

```text
TokenType::semi
```

So:

```text
;
```

becomes:

```text
semi
```

---

# 24. Whitespace

The lexer checks:

```cpp
isspace(c)
```

Whitespace includes things such as:

```text
space
tab
newline
```

Whitespace usually separates tokens but is not itself a meaningful token for our current language.

So:

```text
return     222;
```

can still be interpreted as:

```text
_return
int_lit("222")
semi
```

```cpp
fstream input(...);
```

If we declare:


Wrong:

```cpp
isalnum(...)
```

Wrong:


# 32. Day 1 Code

The complete code as it stands at the end of Day 1.

## `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.10)

project(hydro)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(hydro src/main.cpp)
```

## `src/main.cpp`

```cpp
#include <iostream>
#include <fstream>
#include <sstream>
#include <string>
#include <vector>
#include <optional>

using namespace std;

enum class TokenType {
    _return,
    int_lit,
    semi
};

struct Token {
    TokenType type;
    optional<string> value{};
};

vector<Token> tokenize(string &str) {
    vector<Token> tokens;
    string buf;

    for (size_t i = 0; i < str.length(); i++) {
        char c = str.at(i);

        if (isalpha(c)) {
            buf.push_back(c);
            i++;
            while (i < str.length() && isalnum(str.at(i))) {
                buf.push_back(str.at(i));
                i++;
            }
            i--; // step back, the outer loop will advance again

            if (buf == "return") {
                tokens.push_back({TokenType::_return});
                buf.clear();
            } else {
                cerr << "You messed up!" << endl;
                exit(EXIT_FAILURE);
            }
        } else if (isdigit(c)) {
            buf.push_back(c);
            i++;
            while (i < str.length() && isdigit(str.at(i))) {
                buf.push_back(str.at(i));
                i++;
            }
            i--;

            tokens.push_back({TokenType::int_lit, buf});
            buf.clear();
        } else if (c == ';') {
            tokens.push_back({TokenType::semi});
        } else if (isspace(c)) {
            continue;
        } else {
            cerr << "You messed up!" << endl;
            exit(EXIT_FAILURE);
        }
    }

    return tokens;
}

int main(int argc, char *argv[]) {
    if (argc != 2) {
        cerr << "Incorrect usage. Correct Usage is..." << endl;
        cerr << "hydro <input.hy>" << endl;
        return EXIT_FAILURE;
    }

    string contents;
    {
        fstream input(argv[1], ios::in);
        if (!input.is_open()) {
            cerr << "Error: could not open file " << argv[1] << endl;
            return EXIT_FAILURE;
        }
        stringstream contents_stream;
        contents_stream << input.rdbuf();
        contents = contents_stream.str();
    }

    vector<Token> tokens = tokenize(contents);

    // Day 1 checkpoint: print the tokens we recognized
    for (const Token &token : tokens) {
        switch (token.type) {
            case TokenType::_return:
                cout << "_return" << endl;
                break;
            case TokenType::int_lit:
                cout << "int_lit(\"" << token.value.value() << "\")" << endl;
                break;
            case TokenType::semi:
                cout << "semi" << endl;
                break;
        }
    }

    return EXIT_SUCCESS;
}
```

## Notes on details the sections above left implicit

### The `i--` after each inner loop

When the inner `while` stops, `i` is already on the character that ended the
token: the space after `return`, or the `;` after `222`. Without stepping back,
the outer loop's `i++` skips that character and the semicolon is never
tokenized.

### Checking that the file opened

```cpp
if (!input.is_open()) {
    cerr << "Error: could not open file " << argv[1] << endl;
    return EXIT_FAILURE;
}
```

Without this, a mistyped filename produces zero tokens silently instead of an
error.

### Printing the tokens

The `switch` at the end of `main` is what produces the output box from
section 25. Without it, Hydro tokenizes correctly but appears to do nothing.
